# TRIVAX v0.2 Development Roadmap

Status: experimental development (`0.2.0.dev0`)

Archived baseline: TRIVAX v0.1.1 — DOI `10.5281/zenodo.21989027`

RSMS compatibility target: `1.0-rc.1` (re-audit when RSMS 1.0 becomes stable)

## Scientific objective

v0.2 investigates whether an online controller can detect when delayed-feedback temporal credit is useful and selectively activate it without access to scenario labels or true plant delay.

The primary claim under test is deliberately narrow:

> Online regime selection can approach the better of a lightweight adaptive controller and a temporal-credit controller across changing delayed-feedback regimes while limiting unnecessary temporal-computation cost.

This is a hypothesis, not a release claim.

## Baselines

Every v0.2 benchmark must preserve comparisons against:

1. archived v0.1.x behavior where applicable;
2. Adaptive Hill Climber;
3. Perturb & Observe;
4. TRIVAX Runtime V2 temporal-credit path;
5. selector-disabled ablations.

## Work packages

### WP1 — Selector diagnostics

Expose online quantities required to audit switching decisions:

- temporal score;
- estimated delay and confidence;
- local speed/noise estimates;
- dwell duration;
- switch reason;
- fraction of execution in temporal mode;
- switch count and switch-rate.

### WP2 — Switching-cost model

Measure whether mode changes improve control enough to justify their computational and transient cost. Add regret relative to an offline oracle that chooses the better controller per evaluation segment.

Primary metrics:

- MAE and tail MAE;
- control effort;
- CPU time;
- temporal-mode duty fraction;
- switches per 1000 steps;
- oracle regret;
- worst-regime MAE.

### WP3 — Robust regime detection

Test detector behavior under:

- fixed delays 0, 2, 5, 9;
- abrupt delay changes;
- high and heteroscedastic noise;
- outliers;
- low excitation;
- fast and step-like targets;
- curvature changes.

Avoid tuning directly on holdout scenarios.

### WP4 — Ablation

Compare:

- full selector;
- no hysteresis;
- no delay-confidence term;
- no noise term;
- no dynamic-speed term;
- forced adaptive;
- forced temporal.

Negative results must be retained.

### WP5 — Embedded-readiness profile

Before a v0.2 release candidate, record:

- allocations and state size;
- history/window requirements;
- operations per step or a reproducible proxy;
- Python reference runtime;
- design constraints for an ESP32/STM32/RISC-V port.

No safety-critical deployment claim is permitted from simulation alone.

## Candidate-release gate

A v0.2 candidate should not be declared merely because average MAE improves. It must satisfy all of the following on held-out evaluation:

- reproducible results over multiple seeds;
- no material regression versus the better isolated controller in the majority of tested regimes;
- bounded switching rate;
- measurable benefit over always-temporal execution in computational duty/cost, or measurable control benefit over always-adaptive execution;
- ablation evidence supporting the selector mechanism;
- documented failure regions;
- all tests passing;
- licensing, README, citation metadata, and RSMS compatibility audited.

When these conditions are met, explicitly stop feature expansion and announce: **“Esta versão já é candidata a publicação.”**
